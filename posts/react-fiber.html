01

痛点：旧架构到底卡在哪里

MOTIVATION

先说一个你大概率遇到过的场景：页面上疯狂输入，界面却一顿一顿的。老版本 React 的问题，就出在这。

React 15 及以前，更新走的是递归。当你调用 setState，React 会从根组件开始一口气递归下去：算差异、改 DOM，中间不能停。

问题在于：递归一旦开始，就没人能打断它。如果这棵组件树有 3000 个节点，那么这一整趟计算可能要跑 100ms 以上。而这 100ms 里，浏览器主线程被完全占死 —— 用户点的按钮没反应，输入光标卡住，滚动掉帧。

核心矛盾：浏览器一帧只有约 16.7ms（60fps）。JS 执行、样式计算、布局、绘制都要挤在这 16.7ms 里。React 15 的一次递归渲染很可能一口气吃掉 100ms，等于抢走了 6 帧 —— 用户自然感觉「卡」。

旧架构的两个致命伤

React 15 · 递归栈

  • 无法中断：一旦开始必须跑完
  • 无法区分优先级：所有更新一样急
  • 无法复用：每次都是重新算
  • 阻塞主线程，交互直接掉帧

Fiber 架构 · 可中断链表

  • 可中断、可恢复、可放弃
  • 可排序：高优先级先执行
  • 可复用：为并发特性打地基
  • 让出主线程，交互始终跟手
所以 Fiber 要解决的核心问题，一句话概括：把「一口气干完」变成「分小块干、随时能停、急事优先」。为了实现这三件事，React 必须先把「递归」换成「可暂停的遍历」。
02

Fiber 到底是什么：三个身份，一个东西

DEFINITION

「Fiber」这个词在不同语境下含义不同，这也是初学者最容易懵的地方。你只要记住它有三重身份，它们说的是同一个东西的不同侧面。

01
它是一个数据结构 —— 一个普通的 JS 对象 用来描述「一个组件 / 节点」长什么样，上面挂着 type、props、stateNode、return、child、sibling 等字段。
02
它是一个执行单元 —— 一次可以被打断的小任务 每个 Fiber 节点就是「工作循环」里的一次迭代。处理完一个，检查一下时间够不够，不够就先让给浏览器。
03
它是一种架构 —— 整个 React 16+ 的运行时骨架 调度器（Scheduler）、协调器（Reconciler）、渲染器（Renderer）三层协作，构成了现代 React 的骨架。

核心：Fiber 节点的字段结构

先看这个简化后的对象。你不需要背下来，但要看懂它的链接关系 —— 这正是「可中断遍历」的关键。

fiber-node.jsJS
// 一个 Fiber 节点的核心字段（简化版）
const fiber = {
  // —— 我是谁 ——
  tag: 0,                  // 节点类型标记：函数组件 / 类组件 / HostComponent…
  type: 'div',             // 元素类型，比如 'div' 或函数本身
  key: null,
  stateNode: domElement,    // 对应的真实 DOM 节点（HostComponent 才有）

  // —— 我的状态 ——
  pendingProps: {},          // 本次要用的新 props
  memoizedProps: {},         // 上次渲染用的 props
  memoizedState: null,      // 上次渲染的状态（Hooks 链表就挂在这）

  // ★★★ 树的指针 —— 可中断遍历的根本 ★★★
  return: parentFiber,      // 父节点（不叫 parent，而叫 return：处理完要「返回去」）
  child: firstChildFiber,   // 第一个子节点（只有第一个！）
  sibling: nextSiblingFiber, // 下一个兄弟节点

  // —— 双缓存 ——
  alternate: otherFiber,    // 指向「另一棵树」上对应的节点

  // —— 副作用与优先级 ——
  flags: 0,                // 标记这个节点需要做什么（插入/更新/删除）
  lanes: 0,                // 这个节点包裹了哪些优先级的更新
};
PRINCIPLE 01

child 只指向第一个子节点，其余靠 sibling 串成链表

子节点靠 return 指回父节点，兄弟之间靠 sibling 依次相连。 这三根指针合起来，把「树」变成了一条可以随时停下、随时继续走的路径 —— 这就是 Fiber 能中断的秘密。

为什么用 child / sibling / return，而不是递归？

因为递归用的是 JS 调用栈，而调用栈一旦展开就没法保存进度。用指针手动维护遍历路径，我们就能把「当前走到哪个节点了」存在变量里，随时退出函数、稍后再从那个变量继续。

ReactFiberWorkLoop.jsJS
// 伪代码：Fiber 的「工作循环」核心逻辑
function workLoopConcurrent() {
  // 只要还有活干，且当前帧还有剩余时间
  while (workInProgress !== null && !shouldYield()) {
    workInProgress = performUnitOfWork(workInProgress);
  }
  // 走到这里要么活干完了，要么时间用完了要交还主线程
}

function performUnitOfWork(fiber) {
  // 1. 处理当前节点：算 diff、生成子 Fiber
  const next = beginWork(fiber);

  if (next !== null) {
    return next;          // 有子节点 → 继续往下钻
  }

  // 2. 没有子节点了，开始「收尾」，并往回找兄弟
  let cur = fiber;
  while (cur !== null) {
    completeWork(cur);       // 创建/更新真实 DOM，收集副作用
    if (cur.sibling !== null) {
      return cur.sibling;    // 有兄弟 → 转去处理兄弟
    }
    cur = cur.return;        // 没兄弟 → 回退到父节点
  }
  return null;             // 整棵树都处理完了
}
关键点：performUnitOfWork 每处理完一个 Fiber 就返回一次。回到 while 循环后，会检查 shouldYield() —— 如果这一帧时间用完了，就立刻 break 出循环，把控制权还给浏览器。下次浏览器空闲时从 workInProgress 继续，进度一点不丢。
03

三大核心角色：调度、协调、渲染

ARCHITECTURE

React 16+ 把原来一坨的逻辑拆成了三层，各司其职。理解这三层分工，后面的内容就顺了。

交互演示
一次 setState 之后，到底发生了什么？
点击下方任意一步，看它属于哪一层、干了什么；也可以点「依次演示」看完整链路。这四步走完，页面才真正更新。
S
Scheduler 调度器 · 安排优先级与时机 决定「什么时候执行」。它参考浏览器帧率算出当前还剩多少时间，通过 MessageChannel 在浏览器空闲时唤起任务。
R
Reconciler 协调器 · 找出「要改什么」 这是 Fiber 的主战场。执行 beginWork / completeWork，对比新旧 Fiber 树，算出增删改，把结果标记在 flags 上。
D
Renderer 渲染器 · 真正去改 DOM ReactDOM 负责执行。遍历带 flags 的 Fiber，调用原生 DOM API 完成插入、更新、删除。
P
Browser 浏览器 · 绘制到屏幕 DOM 改完后浏览器做样式计算、布局、绘制。至此用户才看到画面变化。
等待开始 / idle
关键理解：调度器决定「何时」、协调器决定「改什么」、渲染器决定「怎么改」。三者解耦之后，React 才有可能做并发 —— 因为「算」和「改」被拆开了，「算」的过程可以被打断，而「改」是一次性提交的。
角色对应包核心职责能否被打断
调度器scheduler 任务排序、时间片分配、空闲回调本身是调度者
协调器react-reconciler 执行 Fiber 的 begin / complete、diff、打标记 可以（render 阶段）
渲染器react-dom 提交副作用、操作真实 DOM 不可以（commit 阶段）
04

双缓存树：为什么内存里要有两棵树

DOUBLE BUFFERING
这一步理解透了，Fiber 就懂一半了。想象你在画一张图：如果直接在屏幕上改，用户会看到你画到一半的残缺样子。聪明的做法是在草稿纸上画好整张，然后「啪」一下换上去。React 就是这么干的。

React 内存里同时维护着两棵 Fiber 树：

  • current 树 —— 当前正显示在屏幕上的那一棵，用户看到的就是它。
  • workInProgress 树（简称 WIP）—— 正在草稿上构建的那一棵，改动都发生在它身上。
  • 两棵树上对应位置的节点通过 alternate 互相指认，成为一对镜像。

当 WIP 树全部构建完成、副作用收集完毕，React 会执行一个动作：把 root.current 指向 WIP 树。这一瞬间，「草稿」变成了「正稿」，用户看到画面更新。这个过程是一次性、同步、不可打断的。

为什么必须是两棵树？

  • 避免中间态闪烁：用户永远只看到一棵完整的树，不会看到「改了一半」的界面。
  • 支持可中断渲染：WIP 树可以在内存里慢慢构建，构建到一半被打断也没关系，因为屏幕上显示的 current 树完好无损。
  • 复用节点、降低开销：构建 WIP 时会尽量复用 current 树上对应的 Fiber 节点（通过 alternate），而不是全部新建。
  • 让「算」与「改」彻底分开：算的时候随意打断，改的时候集中提交。
CLASSIC 面试题

React 为什么需要双缓存？

标准答案就一句话：为了把渲染过程拆成「可中断的计算」和「不可中断的提交」两个阶段，同时保证用户看不到中间状态。而连接两棵树的桥梁，就是每个 Fiber 上的 alternate 指针。

05

优先级与车道：谁能插队，谁要排队

PRIORITY & LANES
你可能听过 React 会把更新分优先级。但「怎么分」这件事，React 换过好几套方案，最终落到了 Lane（车道） 模型上。我用一个比喻讲清楚。

想象一条高速公路，有 31 条车道（Lane 的实质就是一个 31 位的二进制数）。每一次更新会被分配到一个或多个车道上，车道编号越小、越靠前的，代表优先级越高，跑得越早。

ReactFiberLane.jsJS
// React 源码里 Lane 的定义（节选，用位运算表示）
export const SyncLane            = 0b0000000000000000000000000000001;
export const InputContinuousLane = 0b0000000000000000000000000000100;
export const DefaultLane         = 0b0000000000000000000000000010000;
export const TransitionLane1     = 0b0000000000000000000000001000000;
export const IdleLane            = 0b0010000000000000000000000000000;

// 一个 fiber 可以用 lane 表示「我这个节点上挂了哪些待处理的更新」
fiber.lanes = SyncLane | InputContinuousLane;  // 位运算，一次表示多个

// 判断优先级：取最低位就是当前最高优先级
const nextLane = getHighestPriorityLane(lanes); // lanes & -lanes

01
优先级不是「谁先来谁先执行」，也不是「高的永远赢」

它是一套带饥饿保护的机制 —— 低优先级任务如果一直被打断，React 会逐步提升它的优先级，保证它最终一定能执行完，不会饿死。

高优先级打断低优先级，会重新开始吗？

会，但不是从头开始。这是 Fiber 设计得最精妙的地方之一：如果一次低优先级的渲染工作做到一半，突然来了高优先级更新，React 会：

  1. 放弃当前 WIP 树把已经算了一半的进度丢弃（或者尽可能复用）。
  2. 优先处理高优先级任务用最高的那条 Lane 重新构建。
  3. 高优先级提交完成后再回过头，把低优先级剩下的部分重新算一遍。
为什么能这样：因为 WIP 树是「草稿」，丢了也不影响屏幕上显示的东西。这正是双缓存架构的价值 —— 让「中途放弃」变成了零成本的正常操作，而不是事故。

时间切片：React 是怎么「让路」的

TIME SLICING

前面反复提到「让出主线程」。具体怎么让？答案是通过 shouldYield() 判断 —— 而这个判断来自 Scheduler 对当前帧剩余时间的估算。

Scheduler.jsJS
// scheduler 中的时间片判断（简化）
const frameInterval = 5;  // React 主动把时间片定为 5ms，比一帧还小，留足余量
let deadline = 0;

function shouldYieldToHost() {
  const timeElapsed = getCurrentTime() - startTime;
  return timeElapsed >= frameInterval;   // 超过 5ms 就交还主线程
}

// 用 MessageChannel 而非 setTimeout：宏任务中优先级更高，延迟更小
const channel = new MessageChannel();
channel.port1.onmessage = performWorkUntilDeadline;
function schedulePerformWorkUntilDeadline() {
  channel.port2.postMessage(null);  // 下个宏任务里接着干
}

完整的 render 阶段遍历顺序

把前面的知识串起来：一次 render 阶段的遍历，本质是「深度优先 + 可中断」。走法是这样的：

App ├── Header ← 无 child，completeWork(Header) → 找 sibling └── Main ← 有 child，继续下钻 ├── List ← 无 child，completeWork(List) → 找 sibling └── Aside ← 无 sibling，return 回 Main 遍历顺序（begin 向下，complete 向上）： begin(App) → begin(Header) → complete(Header) → begin(Main) → begin(List) → complete(List) → begin(Aside) → complete(Aside) → complete(Main) → complete(App) → 返回 null，render 结束 ★ 每个 begin / complete 之间都可能被 shouldYield() 打断 ★ 只有 render 阶段可以打断；commit 阶段一旦开始必须跑完
PRINCIPLE 02

render 阶段可中断，commit 阶段不可中断

这就是为什么 React 要求「渲染函数必须是纯函数」—— 因为你可能在渲染到一半时被打断、被丢弃、被重启。 有副作用的代码写在渲染里，就会重复执行，出 bug。

动手：200 行实现一个迷你 Fiber

HANDS-ON
光看不动手，永远记不住。下面这段代码用最精简的方式复刻了 Fiber 的核心思想。你可以直接复制到浏览器控制台跑起来，亲眼看看可中断遍历是怎么回事。
mini-fiber.jsJS
// ═══════ 一个极简版 Fiber 实现 ═══════
// 目标：理解 child / sibling / return 三指针遍历 + 时间切片

let nextUnitOfWork = null;   // 下一个要处理的工作单元
let wipRoot = null;          // work-in-progress 树的根
let currentRoot = null;        // 当前屏幕上的树

// 1. 创建 Fiber 节点：把 vnode 包装成可遍历的 Fiber
function createFiber(element, parent) {
  return {
    type: element.type,
    props: element.props,
    dom: null,
    parent,                   // 相当于 return 指针
    child: null,
    sibling: null,
    alternate: null,        // 指向 old fiber（双缓存）
    effectTag: 'PLACEMENT',  // 副作用标记
  };
}

// 2. 工作循环：带时间切片的遍历
function workLoop(deadline) {
  let shouldYield = false;
  while (nextUnitOfWork && !shouldYield) {
    nextUnitOfWork = performUnitOfWork(nextUnitOfWork);
    shouldYield = deadline.timeRemaining() < 1;  // ★ 时间不够就让路
  }

  if (!nextUnitOfWork && wipRoot) {
    commitRoot();          // 全部算完 → 一次性提交
  }
}

// 3. 处理单个工作单元
function performUnitOfWork(fiber) {
  // (a) 处理自己：创建 DOM
  if (!fiber.dom) fiber.dom = createDom(fiber);

  // (b) 为自己挂上父 DOM（如果是新插入）
  if (fiber.parent) appendToParent(fiber);

  // (c) 为子元素创建 Fiber，串成链表
  let index = 0;
  let prevSibling = null;
  const elements = fiber.props.children || [];
  while (index < elements.length) {
    const childFiber = createFiber(elements[index], fiber);
    if (index === 0) fiber.child = childFiber;
    else prevSibling.sibling = childFiber;
    prevSibling = childFiber;
    index++;
  }

  // (d) 找下一个工作单元：先子 → 后兄弟 → 再回溯
  if (fiber.child) return fiber.child;
  let cur = fiber;
  while (cur) {
    if (cur.sibling) return cur.sibling;
    cur = cur.parent;
  }
  return null;   // 整棵树完成
}

// 4. 提交阶段：一次性把所有 DOM 改动落地（不可打断）
function commitRoot() {
  commitWork(wipRoot.child);
  currentRoot = wipRoot;   // ★ 切换！current 指向新树
  wipRoot = null;
  nextUnitOfWork = null;
}

// 5. render：启动一次渲染
function render(element, container) {
  wipRoot = {
    dom: container,
    props: { children: [element] },
    alternate: currentRoot,       // ★ 挂上旧树，形成双缓存
  };
  nextUnitOfWork = wipRoot;
  requestIdleCallback(workLoop);  // 在浏览器空闲时开始工作
}
跑起来试试：打开任意网页的控制台，粘贴上面代码，然后执行 render({ type: 'div', props: {children: ['hello fiber']} }, document.body)。 你会看到元素出现 —— 虽然只是几十行核心逻辑，但 Fiber 的三指针遍历、时间切片、双缓存切换三件事，它都做到了。

再回头看：Fiber 到底解决了什么

没有 Fiber 时

  • setState 后主线程被占满
  • 输入框打字卡顿、丢字
  • 复杂页面首屏渲染白屏久
  • 无法区分轻重缓急

有了 Fiber 之后

  • 渲染可中断，交互始终跟手
  • 高优先级插队，打字不丢字
  • 可渐进式渲染，白屏更短
  • 并发特性（Transition、Suspense）成为可能

Fiber 没有魔法。
它只是把「一口气干完」拆成了「慢慢来」。

如果你读到了这里，恭喜 —— 你已经掌握了 React 最核心的架构思想。回头看，整个过程其实只有三个关键动作，却撑起了现代 React 的全部并发能力。

① 三指针链表 child / sibling / return 把树变成可暂停的路径，替代了不可中断的递归调用栈。
② 双缓存树 current 与 workInProgress 互为镜像，让「算」可以随便中断，「改」可以原子提交。
③ 优先级车道 用位运算管理 31 条 Lane，让「急事」真的能插队，「慢事」也不会饿死。
④ 时间切片 每 5ms 检查一次是否该让路，把主线程还给人，交互永远优先于后台计算。
⑤ 两阶段提交 render 可中断、commit 不可中断。这也是「渲染函数必须是纯函数」的根本原因。
⑥ 三层架构 Scheduler 决定何时、Reconciler 决定改什么、Renderer 决定怎么改，解耦才能并发。
