原理：MCP 到底解决什么问题

WHY

假设你有 M 个 AI 应用（聊天客户端、IDE 插件、自己写的 Agent）， 要接 N 个外部能力（数据库、监控系统、文件系统、GitHub）。 没有统一协议时，每个应用对每个能力都要写一套适配代码 —— 工作量是 M × N，而且每家的函数签名、鉴权方式、错误码都不一样。

MCP 做的是把这件事**降维**：先规定一套「能力提供方怎么描述自己能干什么」的标准， 于是每个能力只需要实现一次服务端（N 份）， 每个应用只需要实现一次客户端（M 份）， 总工作量变成 N + M。

PRINCIPLE 01

MCP 是「协议」而不是「框架」

它只规定报文长什么样、角色怎么划分、生命周期怎么走， 不规定你用 Python 还是 TypeScript，也不规定你的工具内部怎么实现。 所以一个用 Python 写的服务端，可以被一个 Node 写的客户端直接使用 —— 本文 Step 8 就把两个独立进程的服务端聚合到了同一个 Agent 里。

PRINCIPLE 02

上下文分三类，所有权各不相同

这是本文的主线。MCP 不是把一大坨文本塞给模型，而是把「上下文」按 谁来决定切成三类：模型自己拉的（Tools）、应用主动推的（Resources）、 服务端预置好流程的（Prompts）。理解了所有权，才知道某个需求该用哪一类。

架构：三个角色

  • Host（宿主）：最终用户面对的应用，比如 Claude Desktop、IDE、或者你写的 Agent 脚本。
  • Client（客户端）：Host 内部的一个组件，与一个 Server 保持 1:1 连接。多个 Server 就是多个 Client。
  • Server（服务端）：能力提供方，独立进程，只暴露能力，不关心谁在用。

为什么对话模型选 llama3.2 而不是 qwen3:4b

本案例要跑多轮工具调用，模型必须能稳定输出 tool_calls， 而且要在可接受的时间内返回。实测同一句「查一下 order_api_latency_p99」： llama3.2 → 8.3 秒， qwen3:4b → 29.1 秒（且默认带思维链，单轮实测可达 106 秒）。 两者工具调用参数都正确，但 qwen3 的推理开销让多轮 Agent 变得不可接受。

02

服务端：用 FastMCP 定义三类上下文

SERVER

FastMCP 把三类原语压缩成了三个装饰器： @mcp.tool()、@mcp.resource(uri)、 @mcp.prompt()。函数签名和 docstring 会被自动转成 JSON Schema —— docstring 就是模型看到的工具说明书，写得含糊模型就用不对。

Tools：模型主动拉的上下文

server_ops.pyPYTHON
@mcp.tool()
def search_docs(query: str, top_k: int = 3) -> str:
    """在运维知识库中检索相关段落。

    Args:
        query: 检索词，用自然语言描述你想知道的内容，
               例如「响应变慢怎么排查」「回滚步骤」
        top_k: 返回的段落数量，默认 3
    """
    hits = search_handbook(query, top_k=top_k)
    if not hits:
        return "知识库中没有检索到相关内容。"
    return "\n\n---\n\n".join(
        f"【出处：{name}】相关度 {score:.3f}\n{body}" for name, body, score in hits
    )
PRINCIPLE 03

type hints 决定 schema，docstring 决定模型会不会用

query: str 会被转成 JSON Schema 里的 {"type": "string"}，top_k: int = 3 会带上 default: 3。 而 docstring 里那句「用自然语言描述你想知道的内容」直接影响了模型的传参风格 —— 实测中它正是照这句话把中文问题原样传了进来。

Resources：应用主动推的上下文

server_ops.pyPYTHON
@mcp.resource("handbook://index")
def handbook_index() -> str:
    """知识库目录：列出全部文档及其小节。"""

@mcp.resource("handbook://doc/{name}")     # ← 带占位符 = URI 模板
def handbook_doc(name: str) -> str:
    """按名字读取一篇知识库文档的全文。"""

@mcp.resource("config://order-api")
def service_config() -> str:
    """order-api 的关键运行配置（供排查超时/连接池问题时参考）。"""
注意占位符写法：URI 里带 {name} 的会被注册成 资源模板（resource template），走独立方法 resources/templates/list 查询，不出现在 resources/list 的返回里。作者最初就在这里踩了一次坑 —— 见 Step 3。

Prompts：服务端预置的流程

server_ops.pyPYTHON
@mcp.prompt()
def diagnose(service: str, symptom: str) -> str:
    """生成一份结构化排查提示词。"""
    return (
        f"你是 {service} 的运维值班工程师。当前观察到的症状是：{symptom}。\n\n"
        "请严格按以下流程工作：\n"
        f"1. 先调用 search_docs 检索「{symptom}」相关的排查手册；\n"
        f"2. 再调用 get_service_status 查看 {service} 的实例与健康状态；\n"
        "3. 根据手册指引，调用 get_metric 获取关键指标的实际数值；\n"
        "4. 综合以上信息判断根因，并给出处置建议。\n\n"
        "输出要求：先给「结论」一句话，再给「依据」（引用具体指标数值），"
        "最后给「处置步骤」。不要臆造手册里没有的数字。"
    )

注意这个 prompt 里点名了工具名。这是有意的： 流程和工具由同一个服务端维护，工具改名时 prompt 一起改， 所有客户端自动获得新流程 —— 这正是 Prompts 相对「把流程写死在客户端」的优势。

01
stdout 被协议独占，日志只能走 stderr

stdio 传输下，服务端的 stdout 就是 JSON-RPC 通道。 任何一句多余的 print() 都会污染协议流， 导致客户端解析失败。调试信息请一律用 stderr 或 logging。

03

协议层：手写一个 MCP 客户端

PROTOCOL

上层框架把协议藏得很好，但排查问题时你必须知道线上跑的是什么。 所以这一步不用任何 MCP 客户端库，只用 subprocess + json， 把 stdio 传输的报文一条条打出来。

stdio 传输的规则简单到一句话：一行一个 JSON。 客户端把请求写进服务端 stdin，服务端把响应写回 stdout。

PRINCIPLE 04

能力协商是「先问能不能，再决定做不做」

服务端在 capabilities 里声明自己支持 tools / resources / prompts 中的哪几类。 客户端应当先看这份清单，再决定调用哪些方法 —— 对没声明的能力发起请求属于协议违规。 本文的 ops 服务端三类都声明了，所以后面三种方法都能用。

PRINCIPLE 05

prompts/get 返回的是「消息」，不是「字符串」

返回体是 messages 数组，每条带 role。这意味着服务端可以预置 多轮对话（比如一条 system 定角色、一条 user 给任务、一条 assistant 给范例）， 而不是只能塞一段文本。本文的服务端只用了单条 user 消息，但这个结构值得记住。

04

接入 LangChain：MCP 工具变成 LangChain Tool

ADAPTER

MCP 的 inputSchema 是 JSON Schema， LangChain 的 Tool 要的是 Pydantic 模型。手动转换既啰嗦又容易漏， 所以用官方适配器 langchain-mcp-adapters。 它只做一件事：连接 + 翻译。

04_tools_langchain.pyPYTHON
from langchain_mcp_adapters.client import MultiServerMCPClient

# 连接配置：一个名字 → 一份启动方式
CONNECTIONS = {
    "ops": {
        "transport": "stdio",              # 本地子进程
        "command": sys.executable,         # 用当前解释器
        "args": [str(HERE / "server_ops.py")],
        "cwd": str(HERE),                  # 子进程的工作目录
    }
}

client = MultiServerMCPClient(CONNECTIONS)
tools = await client.get_tools()           # ← 一行拿到全部 LangChain Tool
PRINCIPLE 06

一个名字对应一个连接，一个连接对应一个子进程

字典的 key（"ops"）是你在客户端里给这个服务端起的别名， 后面 get_prompt("ops", ...) 之类的调用都用它定位。 每加一个 key，适配器就多起一个子进程、多走一次 initialize 握手。 所以「多服务端」在 MCP 里是非常轻量的操作 —— Step 8 会用到。

Resources：由应用注入的静态上下文

CONTEXT

Tools 和 Resources 的本质区别不在代码，而在决策权：

  • Tools —— 模型自己决定去「拉」。模型不调，上下文就不存在。
  • Resources —— 应用决定去「推」。读什么、何时读，全在客户端代码里，模型没有发言权。

所以 Resources 适合放「每次都必须知道」的背景资料。这一步用 一个只有读了资源才能答对的问题来验证。

PRINCIPLE 09

Prompts 的价值是「流程与工具同源」

如果把这段排查流程写死在客户端代码里，工具改名时就得逐个客户端升级。 放在服务端则不一样：谁能提供工具，谁就负责写清工具的用法。 所有客户端下次 prompts/get 就自动拿到新流程。 本文的 prompt 里直接点名了 search_docs、 get_service_status、get_metric， 这个耦合是有意为之的。

04
两个 prompt 不要拆成两条消息发

作者最初把 diagnose 和 correlate_change 两个 prompt 作为两条独立消息 一起发过去，结果模型只执行了最后一条 —— 完全跳过 ops 的三个工具，只调了一次变更查询。 合并成一条消息、并显式写「除上述流程外，还必须完成下面的分析」之后才正常。 多段指令务必合并陈述，不要指望模型自己把两条消息都当回事。

常见坑速查

PITFALLS
01
往 stdout 打日志，直接把协议流冲坏

stdio 传输下 stdout 就是 JSON-RPC 通道。一句调试用的 print() 会让客户端解析失败。 调试信息一律走 stderr 或 logging。

02
FastMCP 默认 INFO 日志刷屏

服务端的 stderr 会被客户端继承，每次请求都打印一行 Processing request of type ...， 把教学输出淹没。在服务端里设 mcp.settings.log_level = "WARNING" 即可。 注意这必须写在服务端——在客户端设 logging 级别是没用的。

03
URI 模板不在 resources/list 里

带占位符的资源（handbook://doc/{name}）走独立方法 resources/templates/list。 以为它会出现在 resources/list 的 resourceTemplates 字段里，会拿到空数组。

04
服务端子进程的工作目录不确定

stdio 服务端由客户端启动，cwd 不一定是你以为的目录。 服务端应当在开头把自己所在目录加进 sys.path： sys.path.insert(0, str(Path(__file__).resolve().parent))， 否则 from common import ... 会失败。

05
把 reasoning 模型拿来做多轮 Agent

qwen3:4b 这类带思维链的模型单轮可达 100 秒以上， 多轮工具调用会慢到不可用。reasoning=False 在 ChatOllama 上未必真的关掉思考。 本案例改用 llama3.2，实测 8.3 秒/轮且工具调用正确。

06
LangChain 1.x 的工具返回值是 content blocks

工具返回 [{"type":"text","text":...}] 而不是字符串。 取正文要 result[0]["text"]。 另外 args_schema 在这个版本可能是 dict 而非 Pydantic 模型， 写通用代码时两种形态都要兼容。

07
Docstring 就是给模型看的说明书

模型决定「要不要调、传什么参数」的全部依据就是工具名 + docstring + schema。 docstring 写得含糊，模型就会用错。检索类工具还应注明 「用与知识库相同的语言查询」，否则模型可能自作主张翻译一遍， 把相关度从 1.286 打到 0.583。

08
以为接了工具就不会幻觉

见 Principle 11。工具只保证「真相可达」，不保证「答案正确」。 本例模型把告警阈值 0.85 当成了实测读数，还编了一个不存在的指标。 数值断言校验是必需的。

"""MCP 服务端：把「运维知识库 + 运行时状态」暴露给任意 MCP 客户端。

它演示 MCP 的三类**上下文原语**，这三类正好对应模型拿到上下文的三种方式：

def search_docs(query: str, top_k: int = 3) -> str:
    """在运维知识库中检索相关段落。

    Args:
        query: 检索词，用自然语言描述你想知道的内容，

@mcp.tool()
def get_service_status(service: str) -> str:

    Args:

"""共享配置与检索工具。

所有步骤脚本和服务端都从这里取配置，保证模型名、路径只有一处定义。
"""

from __future__ import annotations

import logging
import re
from pathlib import Path

# MCP SDK 默认会把每次请求的 INFO 日志打到 stderr，会淹没教学输出，关掉
logging.getLogger("mcp").setLevel(logging.WARNING)

# ── 路径 ────────────────────────────────────────────────
BASE_DIR = Path(__file__).resolve().parent
HANDBOOK_DIR = BASE_DIR / "data" / "handbook"

# ── Ollama ──────────────────────────────────────────────
OLLAMA_BASE_URL = "http://127.0.0.1:11434"
# 选型说明：本案例需要模型稳定输出 tool_calls，且要跑多轮。
# 实测同一句「查一下 order_api_latency_p99」：
#   llama3.2  → 8.3s，tool_calls 参数正确
#   qwen3:4b  → 29.1s（且默认带思维链，单轮可达 100s+）
# 所以对话与工具调用统一用 llama3.2。
CHAT_MODEL = "llama3.2:latest"
EMBED_MODEL = "embeddinggemma"  # 备用：需要向量检索时使用

# ── 检索 ────────────────────────────────────────────────
# 中文按单字切，英文/数字按下划线标识符切
_TOKEN_RE = re.compile(r"[A-Za-z_][A-Za-z0-9_]*|[\u4e00-\u9fff]")


def _tokens(text: str) -> list[str]:
    return _TOKEN_RE.findall(text.lower())


def load_sections() -> dict[str, str]:
    """读取知识库，返回 {节名: 正文}，节名即文件名（不含扩展名）。"""
    return {
        p.stem: p.read_text(encoding="utf-8")
        for p in sorted(HANDBOOK_DIR.glob("*.md"))
    }


def split_by_heading(text: str) -> list[tuple[str, str]]:
    """把一篇文档按二级标题切成 [(小节标题, 正文), ...]。"""
    chunks: list[tuple[str, str]] = []
    title, buf = "（前言）", []
    for line in text.splitlines():
        if line.startswith("## "):
            if buf:
                chunks.append((title, "\n".join(buf).strip()))
            title, buf = line[3:].strip(), []
        else:
            buf.append(line)
    if buf:
        chunks.append((title, "\n".join(buf).strip()))
    return chunks


def search_handbook(query: str, top_k: int = 3) -> list[tuple[str, str, float]]:
    """极简词法检索：按查询词元与小节词元的覆盖率打分。

    返回 [(出处, 小节正文, 得分)]，按得分降序。用词法而非向量，
    是为了让本案例聚焦 MCP 协议本身，且结果稳定可复现。
    """
    q = set(_tokens(query))
    if not q:
        return []

    scored: list[tuple[str, str, float]] = []
    for doc_name, text in load_sections().items():
        for title, body in split_by_heading(text):
            hay = set(_tokens(title + "\n" + body))
            if not hay:
                continue
            # 覆盖率为主，标题命中给额外加权
            hit = len(q & hay) / len(q)
            title_hit = len(q & set(_tokens(title))) / len(q)
            score = hit + 0.5 * title_hit
            if score > 0:
                scored.append((f"{doc_name}.md › {title}", body, score))

    scored.sort(key=lambda x: x[2], reverse=True)
    return scored[:top_k]


def banner(title: str) -> None:
    """终端分隔标题，让每一步的输出边界清晰。"""
    print("\n" + "=" * 70)
    print(f"  {title}")
    print("=" * 70)


if __name__ == "__main__":
    banner("自检：知识库与检索")
    secs = load_sections()
    print(f"知识库文件: {list(secs)}")
    print(f"小节总数  : {sum(len(split_by_heading(t)) for t in secs.values())}")
    print("\n检索「响应变慢 连接池」:")
    for name, body, score in search_handbook("响应变慢 连接池", top_k=3):
        print(f"  [{score:.3f}] {name}  ({len(body)} 字)")

@mcp.tool()
def search_changes(service: str, days: int = 3) -> str:
    """查询某个服务最近的变更记录（发布、配置修改）。

    排查线上问题时，「最近有没有变更」往往是关键线索，务必先查。

    Args:
        service: 服务名，可用的有 order-api、inventory-api

@mcp.tool()
def get_change_detail(service: str, version: str) -> str:
    """查询某次具体变更的详情（含变更内容与风险等级）。

    Args:
        service: 服务名
        version: 版本号，如 1.8.2
    """
    for it in _CHANGES.get(service, []):
        if it["version"] == version:

    return f"未找到 {service} 的版本 {version}"
